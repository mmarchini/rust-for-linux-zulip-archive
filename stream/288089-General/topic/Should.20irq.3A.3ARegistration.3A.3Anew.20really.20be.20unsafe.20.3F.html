Topic: Should irq::Registration::new really be unsafe ?

Ewan Chorynski (Jul 29 2026 at 13:31):

Given the current Registration::new function proposed in [1] :

    /// Registers the IRQ handler with the system for the given IRQ number.
    ///
    /// # Safety
    ///
    /// Callers must not `mem::forget()` the returned [`Registration`] or otherwise prevent its
    /// [`Drop`] implementation from running.
    pub unsafe fn new(
        request: IrqRequest<'a>,
        flags: Flags,
        name: &'static CStr,
        handler: impl PinInit<T, Error> + 'a,
    ) -> impl PinInit<Self, Error> + 'a
    where
        T: 'a,

I am failing to find a safe use that would cause an issue by preventing the Drop glue to run.
I understand that if the Drop glue doesn't run and the Registration is deallocated, the irq handler will cause UAF.
But with the pin initialization, I struggle to see how to prevent the drop glue AND free the handler memory.

IIUC, we can use the initiliazer either to create something like Pin<KBox<Registration>> (or another owning type of owning pointer maybe containing a struct containing the registration) and in this case, forgetting the box will leak the handler so no UAF.

We can also use the initializer to pin the Registration on the stack, getting a Pin<&mut Registration> and in this case, we can't call mem::forget on the Registration itself but only on the pinned reference, which won't prevent the Registration Drop glue.

Where is this reasoning going wrong ? Do you have any example of safe code causing issue without the function being unsafe ?

[1]: https://lore.kernel.org/rust-for-linux/20260719153631.559341-1-dakr@kernel.org/

Alice Ryhl (Jul 29 2026 at 13:37):

If T is a struct that contains a reference in a field, then although the T itself must remain valid due to pinning, then the object behind said reference can be destroyed.
