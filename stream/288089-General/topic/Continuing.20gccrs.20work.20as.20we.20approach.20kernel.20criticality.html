Topic: Continuing gccrs work as we approach kernel criticality

Arthur Cohen (Sep 23 2026 at 12:54):

hey everyone :) just posting a message here to say that the gccrs project is getting closer and closer to compiling the kernel, and that we are currently spending a lot of time implementing nightly features that the kernel uses. I think @Pierre-Emmanuel Patry talked about that during Kangrejos. we plan to join the bi-weekly calls you folks have so we can discuss about what the project needs from us and how we can implement that, but please feel free to discuss that here as well, I will be more active on this Zulip in general.

to give you some more details, recently we've worked on the following:

  1. #[used(compiler)] and #[used(linker)] which we had no support for and that are now implemented
  2. #[cfi_encoding] thanks to the help of @Alice Ryhl, but that's also blocked by GCC lacking a CFI implementation, so I'm also trying to help reviewing the patches from @Kees Cook which add it (and will spend more time on that)
  3. #[derive(CoercePointee)] as it's used for your implementation of "alloc types". this one is not complete at all and still needs significant changes to our typechecker but we have early support for the derive itself.

if you can think about anything I'm missing or anything that you think we should pay special attention to, please let me know. I was also asked recently if Rust-for-Linux requires LTO, and if that is the case we may need to make some changes on our end so I want to be ready for that. thank you for all your work and I'm looking forward to doing more compiler crimes so we can support all the features you need!

Alice Ryhl (Sep 23 2026 at 13:01):

LTO is not required, and isn't even really supported with clang in many cases, see depends on !DEBUG_INFO_BTF || (PAHOLE_HAS_LANG_EXCLUDE && !LTO)
