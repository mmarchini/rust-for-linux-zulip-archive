Topic: Should add Data: Send/Sync bounds in configfs::Subsystem?

yilin (Sep 10 2026 at 15:49):

Hi,

I am looking at rust/kernel/configfs.rs and noticed that Subsystem<Data> unconditionally implements Send and Sync:

/// A configfs subsystem.
///
/// This is the top level entrypoint for a configfs hierarchy. To register
/// with configfs, embed a field of this type into your kernel module struct.
#[pin_data(PinnedDrop)]
pub struct Subsystem<Data> {
    #[pin]
    subsystem: Opaque<bindings::configfs_subsystem>,
    #[pin]
    data: Data,
}

// SAFETY: We do not provide any operations on `Subsystem`.
unsafe impl<Data> Sync for Subsystem<Data> {}

// SAFETY: Ownership of `Subsystem` can safely be transferred to other threads.
unsafe impl<Data> Send for Subsystem<Data> {}

However, Subsystem<Data> stores a real Data value, so its Send implementation should at least require Data:Send, and its Sync implementation should require Data:Sync.

It seems possible to register Subsystem<Cell<_>> through safe Rust but Cell doesn't implement Send/Sync.

I know little about this file, so I don't know whether what I say is right. If this is right, I think the minimal change is add Send/Sync bounds:

// SAFETY: `Subsystem<Data>` can only be shared between threads when `Data` is
// safe to share between threads.
unsafe impl<Data: Sync> Sync for Subsystem<Data> {}

// SAFETY: Ownership of `Subsystem<Data>` can only be transferred to another
// thread when ownership of `Data` can also be transferred.
unsafe impl<Data: Send> Send for Subsystem<Data> {}
