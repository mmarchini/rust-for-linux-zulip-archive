SeungJong Ha (Nov 04 2026 at 13:09):

Hello,

I'm trying to migrate the kernel DMA API from transmute.rs to zerocopy, which
@Alistair Popple asked about in June [1]. The bound is on Coherent<T> itself,
so every unsafe impl transmute::{AsBytes, FromBytes} on a type used with it has to
become a zerocopy derive at once. That works on my tree (+16/-19), and the remaining
users are all in nova.

The one I cannot solve is GspFwWprMeta, because it has two anonymous unions.
#[derive(IntoBytes)] on a union needs --cfg zerocopy_derive_union_into_bytes,
which the kernel does not pass, and the most_traits option @Alexandre Courbot
suggested in June [2] gives exactly the same error.

So I think his other option, updating the generator, is the place to fix it. The two
variants of each union are layout-identical and nova only ever writes one, so if the
generator wrote that variant directly instead of a union, the problem would be gone
for r570 and r000 both. The r000 bindings are being added now [3], so this looks like
a good time.

One question first, which I could not answer from the code: @Danilo Krummrich,
does the allocation path of Coherent<T> really need the AsBytes half? The two
SAFETY comments that mention T: AsBytes + FromBytes do not rely on the AsBytes
part, and I found no comment explaining it. If it is not needed there, none of the
above matters.

If I missed something, please let me know.
Best regards, SeungJong

SeungJong Ha (Nov 05 2026 at 05:18):

Alice Ryhl said:

Is there a reason we can't just pass --cfg zerocopy_derive_union_into_bytes?

Thanks, that is really what I wanted to ask.

I did not find a technical reason. I tested it: passing the cfg from the consuming
crate (a RUSTFLAGS_... line in nova's Kbuild) is enough to make the derive compile,
and the padding check still runs, so a union with differently-sized variants is
still rejected.

My only hesitation was the disclaimer Miguel quoted. We would be the first in-tree
user of a cfg that upstream may remove, and "the specific versions of the Rust
toolchain you are using" is a moving target for us.

For nova it may also not be needed at all. nova only uses GspFwWprMetaBootInfo
(the boot variant), and the variants are layout-identical, so the generator could
emit that one directly. That's why I'm suggesting to fix the generator side.

So I am happy either way. Once the bindings have the derives, I can send the dma.rs
series.
