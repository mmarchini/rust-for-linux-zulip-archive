Topic: Locked Vector with Reservations

Philipp Stanner (Nov 25 2026 at 13:17):

Let's say I would want sth like this

// pseudocode

struct Stuff {
    inner: SpinLock<KVec<Foo>>,
}

struct Wrapper {
    s: Stuff,
}

let stuff = KBox::pin_init!(Stuff { new_spin_lock!(KVec::new()) }, GFP_KERNEL);

stuff.inner.lock().reserve(1, GFP_KERNEL)?; // Doesn't work, sleeps with lock held

let wrapper = Wrapper { stuff };

wrapper.insert(42, GFP_ATOMIC)?; // Takes lock, but never allocates because there's a reservation

For an experiment of mine it would be handy to have a vector as a buffer that needs to reserve and then later gets wrapped. After wrapping, it doesn't need to allocate anymore, but can be accessed in parallel.
Before being wrapped, it needs to allocate, but cannot be accessed in parallel, so the spinlock is not yet necessary

Is there a somewhat sane way how I could approach this? I suppose I could wait for a canonical Xarray::reserve :man_shrugging:

(in JobQueue we solve all the pre-allocation issues with carrying our list head and using lists, but that has certain negative aspects to it, too)

Andreas Hindborg (Nov 25 2026 at 13:29):

Not sure how to solve this for KVec. For XArray we are going with sheafs. You need an API that allows you to allocate the memory without taking the lock, and then passing in that memory during the operation under lock.

Andreas Hindborg (Nov 25 2026 at 13:32):

You could add a KVec::reserve_from, passing in an allocation that you can set up before taking the lock.
