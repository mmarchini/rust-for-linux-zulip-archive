Topic: [Feasability] reimplement Illumos doors via module

Gabby Goodrich (Sep 07 2026 at 18:47):

Hello, I wanted to ask what it would take/if it was possible to re-implement the Illumos doors mechanism via a Rust kernel module? For the uninformed, a door is an Illumos specific method of RPC where you can associate a server process and function pointer with a file descriptor, and anybody who uses something like door_call(door_fd, door_func_args_ptr) would automatically spawn an instance of the function pointer on a new thread of the server process given the provided arguments. You could then use fattatch(...) to give the door a searchable file path. Part of my motivation was to make a version of this that includes the ability to call a door like a regular program, then pass all the string arguments (including "executable name") via the door ags pointer, so that you could replace shell scripts or particular programs used for RPC with their lengthy startup process and dependencies on things like RPC frameworks with a simpler and more lightweight alternative.

I will preface that I understand little about Linux kernel module development in general, but I have plenty of experience with both Rust and C, used to read up on general OS dev a lot and still have a relatively solid understanding of what challenges I might experience in development, and figured that a basic implementation of this should be simple enough provided enough reading. It'll probablly turn out to be a little more than I bargained for, but I figured it'd be fun to try anyway.

To my understanding, I will need a way to do the following things:

  • Implement syscalls (to my understanding I would make a file somewhere in /dev/ that programs use ioctl(...) on to talk to my kernel module.)
  • Create custom special files (something like with mknod(...), but ideally without requiring becoming the root user everytime you want to make a door.)
  • Associate a path with the file descriptor, ideally also post creation via door_create(...) (otherwise I don't know how exactly you'd maintain source compatibility without some ridiculous hack like making fattatch(...) a pseudo no-op that returns errors sometimes.)
  • Create threads on the door server process and emplace the function pointer on to them - I dunno how you'd go about this, but my best guess is that you'd create the thread, set it's program counter to point to the entry of the function pointer, and set it's registers/stack to be the arguments sent via the door_call(...) function (maybe in the future I would make it so that the program can determine the ABI to be used, but for now i'll just the platform C ABI.)
  • Somehow make door files executable. Ideally, when a door gets executed via exec(...) there would be no new processes created, that way only fork(...) would create a process that would likely then get destroyed without having copied more than one or two memory pages on the stack and the kernel's own process metadata structure. If I am understanding the docs for binfmt_misc correctly, this isn't possible via binfmt_misc itself since it would need to spawn an interpreter process for the binary at the very least. This might end up being the most difficult part if so (or just entirely infeasible.)
