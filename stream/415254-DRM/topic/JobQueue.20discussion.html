Daniel Almeida (Sep 21 2026 at 13:12):

Hi all,

Today on the JobQueue call, we discussed moving from using the XArray as storage for jobs in the JobQueue to having ListArcs instead.

So as we discussed on the call, my main worry is that, by switching to lists, we may eventually reintroduce problems that @Sami Tolvanen has already fixed in the XArray JQ implementation. There was a lot of work there to make sure that CTS passes without splats and we remain as performant as Panthor in benchmarks. This work will probably transfer over to Nova, Asahi and others. By doing away with the core idea that the queue is a pipeline of jobs in different stages, whose position is tracked via the index allocated by the XArray, this may break in ways we will have to rediscover.

If I understand correctly, there are issues with the current XArray, my proposal is that we fix them. Subsequently, my proposal is that we later switch to the Rust XArray that @Daniel Gomez and @Andreas Hindborg are working on, as that will probably not have these issues from the start if we deliberately try to avoid them.

In any case, although I strongly prefer keeping the XArray design, I understand this may not be the consensus, which is completely understandable in upstream work. I therefore propose we use this topic to collectively discuss some of the issues while @Philipp Stanner iterates on the ListArc code.

Daniel Almeida (Sep 21 2026 at 13:28):

@Philipp Stanner I think you probably need two locks, see https://gitlab.freedesktop.org/panfrost/linux/-/blob/tyr-dev/rust/kernel/drm/job_queue.rs?ref_type=heads#L75 and https://gitlab.freedesktop.org/panfrost/linux/-/blob/tyr-dev/rust/kernel/drm/job_queue.rs?ref_type=heads#L79, otherwise you will probably reintroduce this deadlock:

At the top of each tick(), the pipeline drains entries from
submitted_start..submitted_end into deps_range. This allows the queue to accept
more submissions while the rest of the queue is locked due to a tick being in
progress. Ignoring this separation may cause a deadlock because the driver's
submit() path may take driver locks and then wait on the state mutex held by
tick(), while tick() waits on said driver locks during handler.submit().

The current design solves this lock ordering problem by splitting submit() and
tick() state into two separate locks: inbox for the submission path, and state
for the tick path. The inbox mutex is only held briefly at the top of tick() to
drain new submissions, while the rest of the tick logic (including calls to the
driver's submit()) happens under the state mutex, which is never touched by
submit().

Daniel Almeida (Sep 28 2026 at 22:52):

+cc @Sami Tolvanen @Alice Ryhl

Hi Danilo, following through on what I had promised you on the last
call, starting with the "2 lock" design.

By the way, this was paged out for quite some time. In the process of
going through my notes, I realize that the issue was likely fixed by
rearranging a few data structures in Tyr. I will follow with the full
rationale just in case I missed something:

The problem we originally encountered was that the queue had basically
two points of interaction with the driver, one in the submit ioctl
(where the driver would call prepare()+commit()) and one in the
QueueOps::submit() hook, where the JQ would ask the driver to submit
the work to the ring after deciding it was time to do so.

Let's call the queue's internal lock "state". The problem begins
because QueueOps::submit() is called with "state" held. I believe this
is also the direction Philipp is going with his own design, and it makes
sense: it's a simple lock that allows you to "stop the world" and get a
&mut to the JQ's internal state when running the internal scheduling logic.

So you end up with something like this:

Progress-check JQ thread:

  lock(state)
  QueueOps::submit() // call the driver

In order to submit to the ring, the driver needed to acquire its
own locks as well. Lets assume there's a "Context" driver type that
allows access to the ring buffer, to make things simpler:

Progress-check JQ thread:

  lock(state)
  QueueOps::submit() // call the driver
    // driver code:
    let context = driver.context[i].lock();
    context.ring.push(...);

On the ioctl front, though, this lock was also needed to access the JQ
handle itself:

ioctl thread:

  let context = driver.context[i].lock();
  let jq = &context.job_queue;

  for job in jobs:
    jq.prepare(job)?; // fallible step

  for job in jobs:
    jq.commit(job); // infallible step

In commit(), the JQ must update its internal indices (or lists, or
whatever ends up in the final version) to account for the
newly-submitted work. At this point, it needs to take "state".

So now in the progress-check JQ thread we have:

  lock(state)
  lock(context)

In the ioctl-submit thread we have:

  lock(context)
  lock(state)

Naturally, when running this on the device, it eventually deadlocked,
and we started looking for solutions.

Now, of course there are a few ways to solve this. One of them is to
require drivers to not acquire the same locks from any queue
entrypoint (such as commit() and others), and callbacks (such as
QueueOps::submit() and others). I consider this error-prone.

A second solution is to not lock the queue from any entrypoint. This is
what we chose to do when prototyping. To do so, the indices controlling
the first stage of the queue (i.e.: jobs which have just been submitted)
are protected under a separate mutex, which is never taken by the JQ's
scheduling logic. This was found to work fine on the board.

However I see that we eventually moved the JQ to be a sibling field of
"Context" (which we call Group, in CSF parlance), since the JQ had its
own locking anyway. In this case, at least this lock would not
contribute to a potential ABBA.

I think the fundamental question is, do we want to make this situation
possible at all, to begin with? To have it possible for drivers to
inadvertently run into ABBA issues with the queue by not being careful
like I described above?

Philipp Stanner (Nov 13 2026 at 11:18):

Regarding our RCU problem, I think the solution with the cheapest cost-benefit-ratio would be to combine Daniel's and Gary's suggestions:

  1. We check in DriverFence::drop() whether a grace period has passed already
  2. In the JQ drop worker, we pre-emptively wait for a grace period when a number of jobs has accumulated.

Sth like:

impl<T: JobQueueOps + Send + Sync> ScopedWorkItem for DropWorker<'_, '_, T> {
    fn run(work: &ScopedWork<Self>) {
        let mut jq_locked = work.inner.lock();

        // The fences dropping with their jobs below might do costly calls to
        // `synchronize_rcu()` per job, but they check whether a grace period
        // has passed before doing so.
        //
        // Speed things up by accumulating jobs here.
        if jq_locked.drop_list_count < 100 {
            return;
        }
        drop(jq_locked);
        synchronize_rcu();

        // Synchronize against revocation in `JobQueue::drop`.
        let _lock_guard = work.srcu.read_lock();
        if work.revoked.load(Relaxed) {
            return;
        }

        let mut jq_locked = work.inner.lock();

        while let Some(job) = jq_locked.drop_list.pop_front() {
            drop(jq_locked);
            drop(job);
            jq_locked = work.inner.lock();
        }
    }
}

The number (100) could be specified by the driver at JQ init

Alternatively one might kick the drop worker delayed by one GP, but this would then again fall apart if drivers decide to complete jobs one by one, monotonically increasing the seqno by 1.

What I'm not sure about is how many jobs might get appended to drop-list after this synchronize_rcu(), with new grace periods. But we could have an algorithm for that, like breaking from the loop once drop_list_count jobs have been dropped

Opinions?

Daniel Almeida (Nov 19 2026 at 14:15):

@Danilo Krummrich @Philipp Stanner

For the error handling in Tyr, which was asked last week:

As I said, the firmware reports two error levels in a command stream.

CS_FATAL is documented as unrecoverable. Some IGT tests that caused it were unknown opcodes in the stream, stack overflows and access to unmapped memory. In these cases, we mark the context as dead.

CS_FAULT is documented as recoverable. Some IGT tests that caused it were garbage shader code, garbage framebuffer descriptors or waiting on a GPU sync object that was previously flagged by the firmware with an error.

On CS_FAULT, the stream stops until the driver acknowledges the fault. The firmware then resumes it in a so-called recovery mode, in which instructions are processed but no further GPU work is dispatched. It remains in recovery mode until it finds an ERROR_BARRIER instruction. We have an ERROR_BARRIER right after we return from the user's CS, precisely so we can recover from errors at the job boundary, i.e.: this clears the error state and returns from recovery mode before subsequent jobs execute.

When new jobs execute, they find the firmware in a predictable state that they can then resume from. Sure, the next job might have the failed job as a dependency, in which case the result is likely to not be correct, but this is recoverable regardless, and not a safety issue. Panthor/tyr just return -EINVAL and keep going.

Here is a list of the two types of errors for completeness:

CS_FAULT:
- KABOOM: Shader program executed a KABOOM instruction
- CS_RES_TERM: Iterator terminated
- CS_BUS_FAULT: Command stream bus error
- CS_INHERIT_FAULT: A fault has been inherited
- INSTR_INVALID_PC: Shader invalid Program Counter
- INSTR_INVALID_ENC: Shader invalid instruction
- INSTR_BARRIER_FAULT: Shader barrier failure
- DATA_INVALID_FAULT: Invalid descriptor
- TILE_RANGE_FAULT: Tile out of bounds
- ADDR_RANGE_FAULT: Address out of bounds
- IMPRECISE_FAULT: No detailed error information available
- CSF_RES_EVICTION_TIMEOUT: Firmware error

CS_FATAL:
- CS_CONFIG_FAULT: Command stream config invalid
- CS_UNRECOVERABLE: Command stream marked as unrecoverable. The firmware will not resume it
- CS_ENDPOINT_FAULT: No endpoints available
- CS_BUS_FAULT: Command stream bus error
- CS_INSTR_INVALID: Command stream invalid instruction
- CS_CALL_STACK_OVERFLOW: Command stream call stack overflow
- CSF_FW_INTERNAL_ERROR: Firmware error
