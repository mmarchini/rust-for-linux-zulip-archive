Daniel Almeida (Sep 21 2026 at 13:12):

Hi all,

Today on the JobQueue call, we discussed moving from using the XArray as storage for jobs in the JobQueue to having ListArcs instead.

So as we discussed on the call, my main worry is that, by switching to lists, we may eventually reintroduce problems that @Sami Tolvanen has already fixed in the XArray JQ implementation. There was a lot of work there to make sure that CTS passes without splats and we remain as performant as Panthor in benchmarks. This work will probably transfer over to Nova, Asahi and others. By doing away with the core idea that the queue is a pipeline of jobs in different stages, whose position is tracked via the index allocated by the XArray, this may break in ways we will have to rediscover.

If I understand correctly, there are issues with the current XArray, my proposal is that we fix them. Subsequently, my proposal is that we later switch to the Rust XArray that @Daniel Gomez and @Andreas Hindborg are working on, as that will probably not have these issues from the start if we deliberately try to avoid them.

In any case, although I strongly prefer keeping the XArray design, I understand this may not be the consensus, which is completely understandable in upstream work. I therefore propose we use this topic to collectively discuss some of the issues while @Philipp Stanner iterates on the ListArc code.

Daniel Almeida (Sep 21 2026 at 13:28):

@Philipp Stanner I think you probably need two locks, see https://gitlab.freedesktop.org/panfrost/linux/-/blob/tyr-dev/rust/kernel/drm/job_queue.rs?ref_type=heads#L75 and https://gitlab.freedesktop.org/panfrost/linux/-/blob/tyr-dev/rust/kernel/drm/job_queue.rs?ref_type=heads#L79, otherwise you will probably reintroduce this deadlock:

At the top of each tick(), the pipeline drains entries from
submitted_start..submitted_end into deps_range. This allows the queue to accept
more submissions while the rest of the queue is locked due to a tick being in
progress. Ignoring this separation may cause a deadlock because the driver's
submit() path may take driver locks and then wait on the state mutex held by
tick(), while tick() waits on said driver locks during handler.submit().

The current design solves this lock ordering problem by splitting submit() and
tick() state into two separate locks: inbox for the submission path, and state
for the tick path. The inbox mutex is only held briefly at the top of tick() to
drain new submissions, while the rest of the tick logic (including calls to the
driver's submit()) happens under the state mutex, which is never touched by
submit().

Andreas Hindborg (Sep 21 2026 at 14:47):

If you delete an entry it is accounted for here and when update_node is called after the operation here, if any node was deleted, the node is unlinked and freed if empty here before return. If the delete operation changes the refcount on the root, the tree shrinker is invoked.

So you will not have any empty nodes inside the tree dangling.

But the tree shrinking is an optimization that removes tree levels when the indicies in the tree are small. So when your moving id range moves to the upper part of the tree, you get full depth, which is 6 levels in the normal server configuration, if I remember correctly.
